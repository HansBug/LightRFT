# LightRFT 实验记录撰写规范

## 1. 目的

本文件将 `/home/hansbug/下载/实验记录规范与示例.pdf` 中的要求，整理为适合在本仓库内长期使用的 Markdown 规范。

它的目标不是只给人看一份摘要，而是让 Codex/Claude 在被要求“写实验记录”“整理实验结论”“更新 worklog”“补实验分析”时，可以直接据此产出符合要求的文档。

## 2. 适用范围

以下场景默认适用本规范：

- 在 `plan/` 下新增或更新实验记录、调参记录、排障记录、阶段性 worklog。
- 根据 TensorBoard、W&B、日志、训练脚本、样例输出整理实验分析。
- 对多组 seed、不同超参、不同 reward/rollout 策略做对比记录。

除非用户明确指定写到别处，否则实验记录默认落在 `plan/` 下。

## 3. 核心原则

- 记录必须简洁、清晰、完整，便于后续分析、讨论和继续实验。
- 分析比盲目继续调参更重要。实验后必须写出原因判断和后续动作，而不是只贴结果。
- 优秀实验和失败实验都要记录，不能只保留“看起来最好”的 run。
- 默认使用 3 组及以上 seed 做稳定性判断；如果少于 3 组，必须明确写出原因和当前结论的局限性。
- 所有结论必须基于可核实证据。缺失的信息要显式标成“待补充”或“未核实”，不要编造曲线、指标、截图或结论。
- 实验观察写“事实”，实验分析写“判断与原因”。不要把二者混在一起。
- 对 W&B / TensorBoard 中与本轮问题相关的重要指标，必须明确写出指标名称、指标含义，以及当前数值或走势意味着什么；不能只贴图不解释。

## 4. 推荐实验流程

### 4.1 实验前

- 明确本轮实验目标和要验证的关键假设。
- 确认要比较的参数、实现路径、数据切分和 seed 方案。
- 提前规划好实验命名，确保 `exp_name` 能体现关键参数与 seed。

### 4.2 实验中

- 对同一问题至少跑 3 组及以上 seed，除非当前资源或任务边界明确不允许。
- 保证不同实验之间只有少量、清晰、可比较的变量发生变化。
- 及时保存运行标识、日志目录、W&B/TensorBoard 链接和关键异常样例，避免事后无法补证据。

### 4.3 实验后

- 先收集结果，再做分析。至少收集关键指标、训练曲线和必要的模型输出样例。
- 对比不同 seed 与不同参数设置的表现差异，分析可能原因。
- 根据当前结论制定下一步实验计划，而不是只写“继续调参”。

实验记录不是跑完后补一份流水账，而是实验迭代闭环的一部分。

## 5. 写作前必须收集的信息

在开始写实验记录之前，至少确认以下信息：

- 实验总目标：这轮实验想回答什么问题，解决什么不确定性。
- 实验名称与运行标识：`exp_name`、W&B run 名称、TensorBoard run 标签、启动时间。
- 代码与配置来源：分支名、commit、训练脚本路径、关键配置项、数据集/manifest 路径。
- 资源信息：机器、GPU 数量/型号、并行策略、是否使用 vLLM/SGLang/local HF rollout。
- 关键指标：至少包含与本轮目标相关的核心指标，例如 `collect reward_mean`、`eval reward_mean`、`learn` 相关损失、任务正确率、长度统计、异常率等。
- 指标释义：需要说明每个关键指标反映的是 rollout 质量、训练稳定性、泛化效果、长度控制、抽取失败率，还是其它问题；并说明当前表现意味着什么。
- 曲线证据：`collect` / `eval` / `learn` 的完整可视化截图或可访问链接。
- 现象样例：必要时附模型输出、错误案例、structured output 异常、answer extraction 失败等样例。
- 对比对象：不同 seed、不同超参、不同实现方案之间的差异。
- 下一步动作：下一轮实验要改什么，为什么改。

如果上述信息不全，先写清楚缺口，再开始整理，不要在记录里默认这些信息已经存在。

## 6. 文档开头的固定结构

每份实验记录在页面最开始必须先给出三部分：

### 6.1 总体目标

- 用 1 到 3 条说明本阶段实验的总目标。
- 要回答“这轮实验想验证什么”，而不是只写“跑了哪些命令”。

### 6.2 中间结论

- 先写当前已经比较可信的阶段性判断。
- 结论应尽量带上具体对象、具体指标或具体现象。
- 如果结论尚不稳定，要明确写出“不稳定的原因”或“仍需补验证的部分”。

### 6.3 后续计划

- 写接下来准备做的实验方向或修正动作。
- 计划必须具体，可执行，不能只写“继续优化”“继续观察”。

这三部分是整份文档的导航区，不能省略。

## 7. 每个实验条目的必填内容

默认使用表格记录。表格至少包含以下 3 列：

- `实验`
- `collect/eval TB`
- `learn TB`

其中 `实验` 这一列内部必须再包含 4 项内容：

### 7.1 实验名称

- 写清实验名称和实验目的。
- 名称里尽量包含关键参数缩写，便于后续检索。
- 如果同一组实验只差 seed，也要在名称中明确写出 seed。

### 7.2 实验设置

至少包含：

- 关键超参
- 数据设置
- 训练/推理引擎设置
- 计算资源
- 必要时补充分支、commit、脚本路径、输出目录、W&B 链接

### 7.3 实验观察

- 只写已经观测到的事实。
- 优先写整体趋势、收敛情况、波动区间、不同 seed 的一致性/差异性。
- 尽量带具体数值、步数区间、峰值/回撤区间，而不是只写“效果变好”“比较稳定”。
- 对关键指标要点名写出，例如 `collect reward_mean`、`eval reward_mean`、`actor loss`、`KL`、`response_length`、`answer_extraction_failed` 等，而不是只说“指标正常”或“曲线有变化”。

### 7.4 实验分析

- 解释异常现象和可能原因。
- 明确指出哪些判断是高置信度结论，哪些只是当前推测。
- 对每个被点名的重要指标，都要补一层解释：这个指标本来用来看什么，当前的数值、波动或停滞意味着什么，对训练状态的含义是什么。
- 以 TODO 或下一步动作收尾，说明接下来怎么验证。

## 8. 曲线截图要求

PDF 中对 TensorBoard 截图有明确要求，后续记录默认沿用：

- `collect / eval / learn` 三类曲线都应完整保留在记录中。
- 截图时应尽量关闭左上角的 `Show data download links`。
- 截图时应尽量关闭 `Ignore outliers in chart scaling`。
- `Smoothing` 默认设为 `0`，避免平滑掩盖真实波动。
- 截图中要保留包含实验名和时间的标签，便于回查 run。
- 如果使用的是 W&B，也要提供等价的曲线截图或清晰的图表链接/嵌图。

如果当前拿不到截图，不允许假装已经有图。必须明确写：

- 缺哪一类图
- 预期对应哪个 run
- 当前为什么缺失
- 后续由谁或通过什么路径补齐

## 9. 面向 Codex 的直接执行要求

当 Codex/Claude 被要求“写实验记录”“补实验分析”“整理某轮实验到 `plan/`”时，默认按下面的规则执行：

1. 先读取本文件，再开始写。
2. 先收集证据，再下结论。证据来源优先级通常是：
   - 训练脚本和配置
   - git 分支与 commit
   - TensorBoard / W&B 曲线
   - 日志与 stdout/stderr
   - 模型输出样例
3. 文档开头必须先写 `总体目标 / 中间结论 / 后续计划`。
4. 每个实验条目必须写 `实验名称 / 实验设置 / 实验观察 / 实验分析` 四项，不可省略。
5. `实验观察` 只写事实，`实验分析` 才写推断和后续动作。
6. 默认要求显式比较不同 seed；如果只有 1 到 2 个 seed，要单独写出稳定性不足。
7. 对好的实验和差的实验都要记录，不能只保留最优结果。
8. 对 W&B / TensorBoard 中的重要指标，必须直接点名并解释其含义，不能只贴截图后说“趋势不错”。
9. 对每个关键指标，要额外回答“当前这个状态意味着什么”。例如它意味着训练在收敛、在回撤、只是在过拟合、rollout 质量有提升但泛化没动、长度失控、抽取链路异常等。
10. 不要把原始命令输出整段粘进去；应提炼成可读的实验信息。
11. 不要写空泛判断，例如“效果更好了”“问题解决了”。必须尽量补上指标、步数、波动区间或案例。
12. 如果某项信息缺失，写 `待补充`、`未核实` 或 `当前无法确认`，不要补写想象中的内容。
13. 如果用户没有明确指定格式，默认输出为 Markdown 表格；若表格因截图或内容过宽明显不可读，可以改为“实验小节 + 截图子小节”，但四项必填信息与曲线要求仍然必须保留。

## 10. 推荐的 Markdown 模板

```md
# {实验主题}

## 总体目标

- {本轮实验要回答的问题 1}
- {本轮实验要回答的问题 2}

## 中间结论

- {当前已经可以确认的结论 1}
- {当前已经可以确认的结论 2}

## 后续计划

- {下一步动作 1}
- {下一步动作 2}

## 实验记录

| 实验 | collect/eval TB | learn TB |
| --- | --- | --- |
| **实验名称（和目的）**<br>- `{exp_name}`<br>- {实验目的}<br><br>**实验设置**<br>- {关键超参 1}<br>- {关键超参 2}<br>- {数据/引擎/资源/commit/run 信息}<br><br>**实验观察**<br>- {事实 1，尽量带数值或步数区间}<br>- {事实 2}<br>- {关键指标 A}: {当前数值/走势}<br>- {关键指标 B}: {当前数值/走势}<br><br>**实验分析**<br>- {关键指标 A 的含义}: {它本来反映什么}<br>- {当前指标状态意味着}: {对训练/泛化/稳定性的含义}<br>- {原因分析 2}<br>- TODO: {下一步验证动作} | ![collect/eval]({截图路径或图床链接})<br>{必要时补 run 名称与时间} | ![learn]({截图路径或图床链接})<br>{必要时补 run 名称与时间} |
| **实验名称（和目的）**<br>- `{exp_name}`<br>- {实验目的}<br><br>**实验设置**<br>- {关键设置}<br><br>**实验观察**<br>- {观察}<br>- {关键指标}: {当前表现}<br><br>**实验分析**<br>- {该指标的意义}: {解释}<br>- {当前状态意味着}: {解释}<br>- TODO: {后续动作} | 待补充：{collect/eval 图缺失原因与补充路径} | 待补充：{learn 图缺失原因与补充路径} |
```

## 11. 质量自检清单

交付前至少自查一次：

- 文档开头是否已经写了 `总体目标 / 中间结论 / 后续计划`。
- 每个实验条目是否都包含 `实验名称 / 实验设置 / 实验观察 / 实验分析`。
- 是否同时记录了成功实验和失败实验。
- 是否显式写了 seed 数量以及不同 seed 的差异。
- 是否给出了 `collect/eval/learn` 曲线，或明确说明缺失原因。
- 是否明确点名了关键指标，并分别解释了“指标含义”和“当前状态意味着什么”。
- 是否区分了“已观测事实”和“原因推断”。
- 是否给出了具体的下一步动作，而不是泛泛而谈。
- 是否避免了编造指标、截图、结论或时间线。

## 12. 仓库内的推荐做法

结合 LightRFT 当前协作方式，建议在实验设置或文档附注中优先补充以下信息：

- 分支名与 commit
- 对应训练脚本路径
- 数据 manifest 或数据集切分路径
- 关键运行目录
- W&B 项目 / run 名称
- TensorBoard 日志目录
- 是否是 `local hf rollout`、`vllm` 或 `sglang`

这些不是 PDF 中的硬性原文要求，但对仓库内后续排查、复现实验和跨分支搬运很有价值，建议默认保留。
